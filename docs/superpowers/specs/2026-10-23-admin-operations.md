# 管理端运营模块设计

## 1. 目标与边界

将 `order_sys_admin` 从登录入口与工作台占位页，推进为可直接使用现有微服务接口的校园点餐运营管理端。浏览器只请求 Gateway 的 `/api/**`，不直连 Nacos、MySQL 或各业务服务；身份令牌、刷新与注销继续复用已有 `AuthSession`。

本次只实现当前后端已有、且权限与数据范围能够支撑的管理能力。不新增后端接口，不虚构订单、用户、库存或经营指标。登录页认证行为保持原样；登录后的运营工作区采用独立的视觉 token。

## 2. 后端架构依据

后端按 Gateway、认证、用户、商品、订单、支付、库存、购物车、文件等服务拆分。前端通过 Gateway 访问服务：

```text
Vue 管理端 → Gateway /api/** → 对应业务服务
```

服务发现、服务间调用及数据范围校验由后端负责。前端角色导航只改善体验，不能代替服务端授权。生产反向代理/Nginx 部署不属于本次交付。

业务和权限的主要依据：

- `order_system_cloud/docs/ARCHITECTURE.md`
- `order_system_cloud/docs/API_DOCS.md`
- `order_system_cloud/common-core/.../RoleCode.java`
- `product-service` 的餐厅、档口、分类、菜品管理 Controller 与 Service
- `file-service` 的上传接口及 `ProductImageController`
- `order-service` 的订单、销量榜 Controller
- `user-service` 的角色、状态、数据范围管理 Controller

## 3. 当前 API 能力与本次页面

所有路径均为浏览器访问 Gateway 的 `/api` 前缀。

| 管理能力                | 现有接口                                                                                           | 前端处理                                                                      |
| ----------------------- | -------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 餐厅列表                | `GET /api/products/admin/restaurants`                                                              | 展示当前操作者范围内的餐厅                                                    |
| 餐厅创建                | `POST /api/products/admin/restaurants`                                                             | 仅向总经理展示；服务端仍校验全平台范围                                        |
| 餐厅更新                | `PUT /api/products/admin/restaurants/{restaurantId}`                                               | 餐厅经理只能编辑展示字段；餐厅编码与排序值保持不变                            |
| 餐厅停用                | `DELETE /api/products/admin/restaurants/{restaurantId}`                                            | 仅总经理可操作；需说明当前管理 API 没有重新启用接口，并处理仍有启用档口的 409 |
| 档口查询/创建/更新/停用 | `GET/POST /api/products/admin/windows`、`PUT/DELETE /api/products/admin/windows/{windowId}`        | 档口负责人和餐厅经理；“停用”不是物理删除；营业状态和启停状态分开显示          |
| 分类 CRUD/停用          | `/api/products/admin/windows/{windowId}/categories`、`/api/products/admin/categories/{categoryId}` | 在所选档口的菜单页面维护；`DELETE` 文案使用“停用”                             |
| 菜品 CRUD/下架          | `/api/products/admin/windows/{windowId}/products`、`/api/products/admin/products/{productId}`      | 在所选档口的菜单页面维护；区分在售/下架，不称为删除                           |
| 档口图片                | `POST /api/files/upload` + `PUT /api/products/admin/windows/{windowId}/image`                      | 先有档口 ID，再上传 `WINDOW_IMAGE` 并以 `fileKey` 绑定                        |
| 菜品图片                | `POST /api/files/upload` + `PUT /api/products/admin/products/{productId}/image`                    | 先有菜品 ID，再上传 `PRODUCT_IMAGE` 并以 `fileKey` 绑定                       |

### 3.1 角色导航

| 角色                 | 页面入口                                                                                          |
| -------------------- | ------------------------------------------------------------------------------------------------- |
| `STALL_MANAGER`      | 档口、档口菜单（分类/菜品）                                                                       |
| `RESTAURANT_MANAGER` | 餐厅（仅范围内编辑）、档口、档口菜单                                                              |
| `GENERAL_MANAGER`    | 餐厅（全平台范围时可创建/停用）                                                                   |
| `SYSTEM_ADMIN`       | 当前后端没有可用的用户检索/列表，因此不显示无法完成目标定位的账号管理页；首页说明缺少用户发现接口 |

订单、用户、库存和支付的规则仍由各自服务负责。角色矩阵仅映射当前确认过的 Controller 注解与 Service 数据范围行为；前端隐藏导航不作为安全边界。

## 4. 明确暂缓的后端缺口

- **用户管理**：现有改角色、改状态、改数据范围接口需要 `userUuid`，但没有可用的管理端用户列表/搜索接口，无法安全定位目标账号。当前不做手填 UUID 的管理表单。
- **订单管理**：`GET /orders/list` 和 `GET /orders/{id}` 是当前顾客本人订单；虽有商家状态推进接口，但缺少按商家数据范围返回的订单队列/列表，当前不做订单工作台。
- **库存管理**：当前没有供管理端查询/调整库存的接口，不做库存页面。
- **支付管理**：当前没有管理端支付记录查询接口，不做财务/支付页面。
- **销量榜**：`GET /api/orders/rankings/sales` 是全站累计销量且没有按餐厅/档口范围过滤。不能把全站业务数据展示给范围受限的经理；当前不接入管理端。
- **餐厅图片上传**：没有餐厅图片的专用绑定接口；本次不接受任意图片 URL 作为替代的受控上传方案。

发现以上缺口时先记录，不擅自修改后端 API。若后续要实现这些页面，应先新增与角色范围匹配的查询契约，再接入前端。

## 5. 交互与生命周期约定

- 列表接口目前返回完整数组，没有服务端分页契约；只对已返回的数据做本地关键词筛选，不伪造“总页数/全量查询”能力。用户输入采用即时本地过滤，清空按钮可键盘访问。
- 创建/编辑在服务端成功前保留表单；成功后回到所属列表并给出共享成功提示。请求失败保留输入并在表单内显示错误。
- 远端修改采用悲观更新，禁止重复提交。收到 401 时复用 AuthSession 的续期/清会话流程；收到 403 时在当前上下文说明权限/数据范围不足，不伪装成 404。
- 停用/下架只在服务端确认后从当前视图更新。危险操作使用应用内确认对话框，说明确切对象与影响。餐厅停用单独说明不可通过当前管理接口恢复；档口状态与营业状态不合并。
- 菜品、档口图片必须通过文件服务。限制 JPG/PNG/GIF/WebP，客户端限制 5 MB（服务端仍为最终校验）；确定绑定失败后才逻辑删除新上传文件。网络中断或 5xx 可能发生在服务端提交后，必须重读实体核实；不能确认时保留文件并提示用户复核，避免误删已生效图片。
- 可见空状态、无匹配结果、加载、失败、403 和会话过期均由真实请求状态驱动，不用静态示例数据。
- 所有写表单使用应用内验证、关联错误文本和 `novalidate`，重复提交禁用；状态等有限枚举使用原生 `<select>`，接受系统弹出层外观。
- 使用语义化表格、键盘可达按钮、可见焦点、缩小屏幕下水平表格滚动/优先级布局；动效尊重 `prefers-reduced-motion`。

## 6. 工作区视觉方向

管理工作区和登录入口是同一产品的两个有意区分的表面：登录页保留现有橙色/深绿身份视觉；登录后的运营端采用“校园食堂窗口牌与值班台账”的冷色系统。工作区以深石墨蓝导航、瓷青操作色、少量麦芽金标记状态，避免把登录页主题机械铺到高密度运营表格。

- 深色导航：`#142B35`
- 主要操作（瓷青）：`#087A78`
- 重点/当前项（麦芽金）：`#D3A447`
- 工作区底色：`#EEF3F1`
- 内容表面：`#FCFDFC`
- 分隔线：`#D5DFDC`
- 主文字：`#203239`
- 次级文字：`#64777A`
- 危险/成功：`#AA4039` / `#2C7358`

排版采用系统中文无衬线字体，数据 ID/编码可用等宽字。桌面使用稳定的左侧运营导航与宽内容区；窄屏将导航移入明确的抽屉控件，页面自然纵向滚动。单一视觉签名是侧栏“窗口挂牌”——当前业务入口以短麦芽金挂牌从深色侧栏伸出；表格、卡片和表单保持克制，强调数据层级，不用虚构 KPI、渐变玻璃或装饰性动态图表。

颜色由 runtime `src/assets/tokens.css` 持有，`DESIGN.md` 镜像并解释；运营端 token 使用 `--ops-*` 并限定在运营工作区，现有登录页 `--color-*` 不改含义。

## 7. 交付标准

- 架构/接口/角色边界写入管理端文档，标明真实实现与暂缓缺口。
- 登录认证链路无行为回归；仅新增工作区路由与页面。
- 已开放的餐厅、档口、分类、菜品和图片流程只调用现有 API。
- 不产生虚假数据、不新增业务后端接口、不把全站销量暴露到管理端。
- 按用户要求不编写/运行自动化测试；运行类型检查和生产构建，并在可用浏览器中核验主要页面、窄屏、加载/失败/空态与对话框。
- 每个可独立审阅的阶段形成一个提交；约 2026-10-23 07:00（Asia/Shanghai）核对分支与构建后推送当前功能分支，不 force push，不关机。
